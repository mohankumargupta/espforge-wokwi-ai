## APDS9960 — RGBC high-byte registers silently read as zero

**Device:** APDS9960 (gesture / proximity / RGBC ambient light sensor, I2C)
**File:** `chip.zig`, function `readReg`
**Symptom:** ESPHome logged `clear=0.1% red=0.2% green=0.3% blue=0.0%` instead
of the expected canonical defaults `clear=20.0% red=15.0% green=12.0% blue=9.0%`.
Proximity (`7.1%`) was correct. The `qa_test` Rust harness timed out waiting
for `"Clear channel = 20.0 %"` on the Wokwi serial stream.

**Root cause:** `readReg`'s dispatch switch matched only the *low-byte*
register address of each 16-bit RGBC channel pair:

```zig
fn readReg(chip: *ChipState, reg: u8) u8 {
    return switch (reg) {
        R.id => 0xAB,
        R.status => computeStatus(chip),
        R.cdata, R.rdata, R.gdata, R.bdata => rgbcByte(chip, reg),  // 0x94, 0x96, 0x98, 0x9A only
        R.pdata => proxCountFromPercent(proxPct(chip)),
        else => chip.regs[reg],   // <-- 0x95, 0x97, 0x99, 0x9B fall through here
    };
}
```

`R.cdata`/`R.rdata`/`R.gdata`/`R.bdata` are single addresses (`0x94`, `0x96`,
`0x98`, `0x9A`), not ranges. The corresponding high-byte addresses (`0x95`,
`0x97`, `0x99`, `0x9B`) fell to `else => chip.regs[reg]`, which is the raw
backing array — zero-initialized at reset and never written, since ESPHome
only *reads* those addresses. Every RGBC channel's high byte therefore always
read `0x00`, truncating a 16-bit count down to its low byte alone:

| Channel | Expected count | Actual (high byte forced to 0) | % |
|---|---|---|---|
| clear | 13107 (`0x3333`) | `0x0033` = 51 | 0.1% |
| red | 9830 (`0x2666`) | `0x0066` = 102 | 0.2% |
| green | 7864 (`0x1EB8`) | `0x00B8` = 184 | 0.3% |
| blue | 5898 (`0x170A`) | `0x000A` = 10 | 0.0% |

All four match the observed buggy output exactly. Proximity is a single-byte
register (`0x9C`), so it has no high/low split and was unaffected — which is
why it was the one channel reading correctly, and a useful diagnostic signal:
**when only the multi-byte registers are wrong and single-byte registers are
fine, suspect a low/high dispatch gap, not the conversion functions.**

**Why existing tests didn't catch it:** `chip.zig`'s test suite exercised the
*conversion functions* (`rgbcCountFromPercent`, `rgbcToBytes`, etc.) directly
and asserted they produced the correct bytes — which they did. Nothing called
`readReg` itself across the full register address range, so the dispatch bug
sitting *between* the correct encoder and the I2C wire was invisible to
`zig build test`. It was only caught downstream, after a full ESPHome compile
and Wokwi simulation run, via the `qa_test` timeout.

**Fix:** widen the switch arm to a range covering the whole multi-byte block,
using Zig's inclusive range syntax:

```zig
R.cdata...R.bdata + 1 => rgbcByte(chip, reg), // 0x94..0x9B inclusive
```

(`R.cdata` = `0x94`, `R.bdata` = `0x9A`, so `R.bdata + 1` = `0x9B` — the full
CDATAL..BDATAH span.) The same bug existed in `writeReg`'s read-only guard,
which likewise only blocked writes to the low-byte addresses, leaving
`0x95/0x97/0x99/0x9B` writable when they should be read-only data registers.

**Generalized lesson:** any register-based chip with multi-byte values (16-bit
counts split across two 8-bit addresses, 24-bit, etc.) is at risk of this
exact bug if the dispatch table lists only one representative address per
logical register instead of the full byte span. Test the dispatch function
itself (`readReg`/`writeReg`) by iterating every address in the register map
— including every byte of every multi-byte register — not just the encoder
functions in isolation. See `wokwi-customchip/SKILL.md` Step 4a.

## APDS9960 — spec's inline `CountMAX` formula contradicts its own worked examples

**Device:** APDS9960
**File:** `spec_apds9960.md` / `prompt0c/src/main.zig`, function `atimeToFullScale`
**Symptom:** none observed at runtime (caught during spec authoring, before
implementation) — flagged here because it's the same *class* of risk as the
register-dispatch bug: an authoritative-looking spec statement was wrong.

**Root cause:** the datasheet's Data Conversion section states
`CountMAX = min(1025 × CYCLES, 65535)`, but the datasheet's own worked-example
table gives `ATIME=0xF6 → CountMAX=10241` and `ATIME=0xDB → CountMAX=37889`,
both of which only satisfy `min(1024 × CYCLES + 1, 65535)`. The two constants
(`1025×` vs `1024×+1`) disagree for every CYCLES value except the boundary
cases (0xFF and 0x00).

**Fix / rule applied:** treated the worked-example table as authoritative over
the inline prose formula (worked examples are directly testable; prose is
not), implemented `1024 * cycles + 1`, and recorded the discrepancy explicitly
in `conversions_manifest.md` rather than silently picking one. See
`data-conversions-complex-logic/SKILL.md`, "Resolving contradictions within
the spec itself."

## APDS9960 — sign/magnitude offset registers have two encodings of zero

**Device:** APDS9960 (`POFFSET_UR`/`POFFSET_DL`/`GOFFSET_*` registers)
**File:** `prompt0c/src/main.zig`, `offsetFromByte`/`offsetToByte`

**Symptom:** an exhaustive "every byte round-trips through decode→encode"
test failed for a *correct* implementation.

**Root cause:** sign/magnitude 8-bit encoding has two representations of
zero: `0x00` (positive zero) and `0x80` (negative zero, sign bit set, zero
magnitude). `offsetFromByte(0x80) == 0`, but a canonical encoder for `0`
necessarily returns only one of `0x00`/`0x80` — so round-tripping `0x80`
through decode-then-encode does not return `0x80`.

**Fix:** canonicalized `0x80` → `0` on decode, chose `0x00` as the sole
canonical encoding of zero, and excluded `0x80` from the exhaustive
round-trip test (documented as a deliberate exclusion, not a gap). See
`data-conversions-complex-logic/SKILL.md`, "Duplicate encodings of the same
value."
